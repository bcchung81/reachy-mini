## SLO 판정

```
VAD hangover 0.30 + STT 최악 0.25 + (LLM 첫 절 + 합성) 최악 1.12 = 1.67s
```

**SLO 2.0s 만족.** 실제로는 더 빠르다 — 인자 없는 `say`는 합성과 재생이 겹쳐
파일 출력보다 이르게 소리가 나기 시작한다. 1.67s는 보수적 상한이다.

## 개정 (2026-07-29 저녁) — 자연스러움 우선으로 재조정

음성 시연에서 두 가지 문제가 나왔다.

1. **답변이 뚝뚝 끊긴다.** 절 분할이 30자마다 공백에서 잘라
   `"…바탕으로 대화하고" / "있습니다."` 처럼 문장 한가운데를 쪼갰다.
   절마다 `say` 프로세스가 따로 뜨므로 경계에 공백과 억양 초기화가 생긴다.
2. **질문이 끝나기 전에 끊긴다.** VAD hangover 0.30초가 너무 짧다.
   한국어는 종결어미 앞에서 뜸을 들이는 일이 흔해(`"…어디까지 [쉼] 있어?"`)
   그 틈에 발화가 종료됐다.

`say -f -`로 프로세스 하나에 이어 먹이는 방법을 검토했으나 **EOF까지 버퍼링**한다
(실측: 5초 대기 후 통째 발화, 총 8.8초). 스트리밍 발화는 불가능하다.

## 예열 — llama-server 슬롯은 개수만큼 태워야 한다 (2026-07-29 저녁)

`scripts/warmup.py`가 LLM·TTS·STT·모션 카탈로그를 한 번씩 태운다. 기동 스크립트가
앱 진입 직전에 자동 실행하므로 첫 질문이 프리필 비용을 물지 않는다.

두 가지를 실측으로 잡았다.

**① 시스템 블록이 같아야 캐시가 맞는다.** llama.cpp 프리픽스 캐시는 실제 토큰
접두사로 잡힌다. 시스템 프롬프트 없이 `"안녕"`만 보내 예열하면 접두사가 달라
앱의 첫 요청이 그대로 프리필한다. 예열도 `prompt.md`를 실어 보낸다.

**② 슬롯이 여러 개다.** 현재 구성은 `parallel=2`(슬롯 2개, 슬롯당 ctx 8192)다.
한 번만 예열하면 슬롯 하나만 캐시가 차고, 다른 슬롯으로 간 요청이 튄다.

| 예열 방식 | TTFT |
|---|---|
| 1회만 | 0.088s / **0.399s** 교대 |
| 슬롯 수만큼(3회) | 0.088~0.103s 균일 (18회 연속 측정) |

콜드 스타트 직후 예열 로그의 `TTFT 0.34s → 0.05s`가 이 과정을 보여준다.
슬롯 수를 늘리면 `warmup.py`의 `LLM_WARM_ROUNDS`도 함께 올린다.

## 지연 재측정 — TTS 교체 후 (2026-07-30)

음색을 Qwen3-TTS(serena)로 바꾼 뒤 전 구간을 다시 쟀다. **가정이 뒤집혔다.**

| 구간 | 실측 | 비중 |
|---|---|---|
| ~~afplay 기동~~ → 상주 스트림 | ~~0.80s~~ → **0.00s** | ~~31%~~ |
| VAD hangover | 0.70s | 설정값 |
| TTS 합성 | 0.54s | |
| STT | 0.49s | |
| LLM 첫 절 | **0.07s** | **3%** |

**LLM 은 전체의 3% 다.** 설계 초기에 LLM 을 지배적 병목으로 본 가정(§8)은
스키마 제약을 뺀 뒤로 완전히 무효다. 여기를 더 파도 얻을 게 없다.

### afplay 는 발화당 0.8초 고정비였다

`afplay` 는 프로세스를 띄워 CoreAudio 를 매번 초기화한다. **파일 길이와 무관**하다:

| 파일 길이 | 총시간 | 오버헤드 |
|---|---|---|
| 0.1s | 0.83s | 0.73s |
| 0.5s | 1.34s | 0.84s |
| 1.0s | 1.85s | 0.85s |
| 2.0s | 2.87s | 0.87s |

`sounddevice` 상주 스트림으로 바꾸니 개설 0.014초(1회), 이후 오버헤드 **0.00초**다.
`StreamPlayer` 가 이를 담당하고, 장치를 못 열면 `afplay` 로 물러난다.

**발화 종료 → 첫 오디오: 2.60초 → 1.80초.**

### 남은 후보 (미적용)

- **VAD hangover 0.70 → 0.50**: -0.20초. 다만 질문이 잘리는 문제가 재발하면
  체감이 훨씬 나쁘다. 낭독 테스트로 확인하고 조심히 내릴 것.
- **고정 대사 사전 렌더링**: 해당 발화의 합성 0.54초가 0 이 된다. 대본은 시드까지
  고정돼 있어(selfintro.SEEDS) 파일로 떠도 같은 소리가 보장된다.
- **STT(0.49초)** 는 건드리지 말 것. 더 작은 모델은 짧은 한국어에서 오인식이 는다.

## 관찰 (`say` 시절 — 아래 1·2번은 해소됐다)

- ~~**병목이 LLM에서 TTS로 옮겨갔다.**~~ 설계문서 §8은 LLM(1.2s)을 지배적 비용으로
  봤으나, 스키마 제약을 뺀 자유 생성에서는 LLM이 0.5s 이하이고 `say`가 0.8~0.9s로
  가장 컸다. → **해소.** 위 [TTS 교체 후](#지연-재측정--tts-교체-후-2026-07-30) 참고.
  Qwen3-TTS 상주 서버로 바꿔 첫 절 합성이 **0.40s** 다(0.6B CustomVoice/serena,
  speed 1.2, HTTP 왕복 실측). LLM 이 3%, TTS 도 더 이상 지배적이지 않다.
- ~~`say` 비용의 대부분은 프로세스 기동 고정비다 … 더 줄이려면 상주 TTS로 바꿔야 한다~~
  → **그렇게 했다.** 절 길이와 무관한 고정비였다는 진단은 맞았고, 상주 TTS 로 옮겨
  사라졌다. 다만 성격이 바뀌었다 — Qwen3-TTS 는 **합성 시간이 절 길이에 비례**하므로
  (RTF 0.34) 이제 절을 잘게 쪼개는 것이 유리하다. `speak_many` 가 그렇게 한다.
- `afplay` 기동 0.8초 고정비도 상주 스트림으로 제거했다(위 절 참고).
- 스트리밍 파싱은 반드시 **바이트 단위 줄 분할** 후 줄 단위 디코드여야 한다.
  `requests.iter_lines(decode_unicode=True)`는 청크 경계에서 한글 멀티바이트를 쪼개
  `JSONDecodeError: Unterminated string`를 낸다(실측 확인). `llm.py`도 같은 방식이다.
