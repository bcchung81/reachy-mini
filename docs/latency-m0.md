- 측정일: 2026-07-29
- 환경: macOS 26.5.2 / Apple M5 Pro / 48GB / Python 3.12.13
- LLM: `unsloth/gemma-4-E4B-it-GGUF:Q4_K_M` @ llama-server :8080 (`--reasoning off`)
- TTS: macOS `say -v Yuna`
- 스크립트: `scripts/measure_latency.py`

## 측정값

| TTFT | 첫 절 | LLM 전체 | 합성 | 질문 → 첫 절 |
|---|---|---|---|---|
| 0.03 | 0.05 | 0.30 | 0.90 | 안녕, 오늘 기분 어때? → `안녕하세요!` |
| 0.08 | 0.21 | 0.45 | 0.79 | 점심에 뭐 먹을지 고민이야. → `맛있는 거 많이 고민되시죠?` |
| 0.08 | 0.31 | 0.52 | 0.81 | 재밌는 얘기 하나 해줘. → `오늘 아침에 커피를 마시다가 재미있는 생각을 했어.` |

단위 초. **합성**은 `say -v Yuna -o clause.aiff` — 재생을 뺀 순수 합성 시간이다.
인자 없는 `say`는 재생 완료까지 블록되어 합성 지연과 오디오 길이가 섞이므로 쓰지 않았다.

## SLO 판정

```
VAD hangover 0.30 + STT 최악 0.25 + (LLM 첫 절 + 합성) 최악 1.12 = 1.67s
```

**SLO 2.0s 만족.** 실제로는 더 빠르다 — 인자 없는 `say`는 합성과 재생이 겹쳐
파일 출력보다 이르게 소리가 나기 시작한다. 1.67s는 보수적 상한이다.

## 관찰

- **병목이 LLM에서 TTS로 옮겨갔다.** 설계문서 §8은 LLM(1.2s)을 지배적 비용으로 봤으나,
  스키마 제약을 뺀 자유 생성에서는 LLM이 0.5s 이하이고 `say`가 0.8~0.9s로 가장 크다.
- `say` 비용의 대부분은 **프로세스 기동 고정비**다. 짧은 절("안녕하세요!", 6자)이
  0.90s, 긴 절(24자)이 0.81s로 길이와 무관하다. 절을 잘게 쪼갤 이유가 없다는 뜻이며,
  더 줄이려면 `say` 대신 상주 TTS(Piper 서버 등)로 바꿔야 한다 — 현재 SLO는 만족하므로 보류.
- 스트리밍 파싱은 반드시 **바이트 단위 줄 분할** 후 줄 단위 디코드여야 한다.
  `requests.iter_lines(decode_unicode=True)`는 청크 경계에서 한글 멀티바이트를 쪼개
  `JSONDecodeError: Unterminated string`를 낸다(실측 확인). `llm.py`도 같은 방식이다.
