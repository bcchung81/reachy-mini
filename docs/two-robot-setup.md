시연 전에 **사람이 해야 하는 일**만 모았다. 코드는 다 됐고, 여기서부터는 기기·네트워크·확인이다.
근거는 `docs/superpowers/specs/2026-09-11-two-robot-mc-docent-design.md` §6·§9.

## 1. WiFi 등록 — ⚠️ **반드시 한 대씩**

두 로봇 모두 처음 켜면 자기 핫스팟을 띄우는데, **SSID가 `reachy-mini-ap` 로 똑같다**
(`daemon/app/routers/wifi_config.py:25`). 둘을 동시에 켜두면 노트북이 어느 쪽에 붙었는지
알 방법이 없고, 사회자 설정이 도슨트에 들어간다.

### 순서

1. **A만 켠다.** B는 전원을 끈 채로 둔다.
2. 노트북에서 **Reachy Mini Control** 실행 → 하단 **"First time connecting…"**
3. 안내대로 로봇 핫스팟(`reachy-mini-ap`)에 노트북을 접속
4. 전용 공유기의 SSID·비번 입력 → 로봇이 그 망으로 재접속
5. 연결 확인 후 **A를 끈다**
6. **B만 켜고** 2~4를 반복
7. 둘 다 켠다

> **핫스팟이 안 보이면** — Control 앱의 "Try the Bluetooth Console" 로 간다.
> Chrome·Edge·Opera 에서 Web Bluetooth 로 붙어 핫스팟 리셋·네트워크 상태를 볼 수 있다.

### 왜 전용 공유기인가

- 시연장 공용 AP는 **AP isolation** 이 켜진 경우가 많다 → 노트북↔로봇 통신이 아예 막힌다
- 로봇 데몬의 REST/WebSocket API에 **인증이 없다**. Wireless 는 `0.0.0.0` 에 바인드한다
  (`daemon/app/main.py:119`) — 공용망에 올리면 누구나 로봇을 조작할 수 있다
- Wireless 안테나는 2.79 dBi 패치 하나뿐이다. 공유기를 로봇 가까이 둔다. 5GHz 권장

## 2. 고정 IP 배정 — ⚠️ `reachy-mini.local` 을 믿지 않는다

두 로봇의 hostname이 **둘 다 `reachy-mini`** 다. `.local` 이 어느 쪽을 가리키는지
보장되지 않고, 부팅 순서에 따라 바뀐다.

공유기 관리페이지에서 **MAC 기준 DHCP 고정 IP**를 배정한다.

```
사회자  192.168.0.4
도슨트  192.168.0.5
노트북  192.168.0.10        (무대감독·추론 3종이 여기)
```

이 두 주소가 `./reachy.sh start --robot` 의 **기본값**이다(§7). 대역이 달라 다른 주소를 주면
**적어두고** 기동할 때 `REACHY_MC_HOST`/`REACHY_DOCENT_HOST` 로 덮어쓴다 — 안 그러면 기본값
주소로 엉뚱한 기기를 찾는다.

### 확인

```bash
curl -s http://192.168.0.4:8000/api/daemon/status | head -c 200
curl -s http://192.168.0.5:8000/api/daemon/status | head -c 200
```

둘 다 JSON이 나와야 한다. 안 나오면 IP가 틀렸거나 같은 망이 아니다.

## 3. 기기 식별자(`unit_id`) 채취 — 두 대가 뒤바뀌는 사고를 막는다

로봇마다 하드웨어 고유 ID가 있다. 무대감독이 기동할 때 이 값을 대조해서
**사회자 자리에 도슨트가 있으면 즉시 실패**한다. 시연장에서 "왜 얘가 저 대사를 하지"를
추적하는 것보다 기동에서 막는 게 싸다.

```bash
curl -s http://192.168.0.4:8000/api/daemon/status | python3 -c "import sys,json;print(json.load(sys.stdin)['hardware_id'])"
curl -s http://192.168.0.5:8000/api/daemon/status | python3 -c "import sys,json;print(json.load(sys.stdin)['hardware_id'])"
```

나온 값을 적어둔다. **`null` 이 나오면** 그 로봇은 Wireless 가 아니거나 오디오 장치가
안 잡힌 것이다 — 시뮬에서는 언제나 `null` 이지만 실기에서는 값이 있어야 한다
(`get_hardware_id()` 가 리눅스 sysfs 를 읽는다, `docs/lessons.md`).

> 이 값은 **노트북의 `REACHY_MC_UNIT` / `REACHY_DOCENT_UNIT`** 에 넣는다(§6).
> `scripts/stage-env.sh` 에는 이 항목이 없다 — 그 스크립트는 로봇 쪽 값만 다룬다.
> 검증하는 쪽이 감독(노트북)이기 때문이다.

뜬다. 데스크톱 앱을 새로 깔 필요 없이, 대시보드가 하던 일은 **REST API로 직접**

```bash
curl -s http://<로봇IP>:8000/api/apps/startup-app
# {"startup_app": null}  ← 이게 나오면 이미 끝난 것, 손댈 것 없다

curl -s -X PUT http://<로봇IP>:8000/api/apps/startup-app \
  -H 'Content-Type: application/json' -d '{"startup_app": null}'
```

(`daemon/robot_app_lock.py`). 온보드 앱이 켜져 있으면 우리 앱과 모터를 두고 싸운다.

**두 대 모두** 확인한다.

## 5. 물리 배치와 라벨

- 두 로봇을 **서로 마주보되 관람객도 보이는** 각도로 놓는다
- 로봇 본체에 **사회자 / 도슨트 라벨**을 붙인다. 겉모습이 같아서 운영 중에 헷갈린다
- 스피커 음량을 귀로 맞춘다 — 한쪽이 묻히면 대화로 안 들린다

### ⚠️ 시선(`gaze`)은 **아직 머리를 움직이지 않는다**

큐시트의 `gaze: partner` / `audience` 는 감독이 로봇에게 보내지만, 로봇 쪽
`on_gaze` 는 **로그 한 줄을 찍을 뿐**이다(`main.py`). 머리 각도를 계산하지도,
`ReachyMini` 에 목표를 주지도 않는다.

```python
on_gaze=lambda target: print(f"  [시선 {target}]"),
```

그래서 물리 배치가 시선 연출을 좌우하지 **않는다** — 지금은 배치를 어떻게 하든
로봇 머리는 그대로다. 배치는 관람객이 두 로봇을 다 보고 듣는 데만 영향을 준다.

나중에 시선을 실제로 붙이려면 상대 로봇의 방향(머리 yaw 상수)을 로봇마다 재서
넣어야 하고, 그때 비로소 이 항목이 배치에 의존하게 된다. **그전까지 이 문서가
배치를 시선의 전제로 적으면 운영자가 있지도 않은 동작을 맞추느라 시간을 쓴다.**

## 6. 설정 채우기 — ⚠️ **로봇에서 `export` 하지 않는다**

로봇의 앱은 `POST /api/apps/start-app/` 로 **데몬(systemd)이 낳는 자식 프로세스**다.
로봇에 SSH로 들어가 `export REACHY_ROLE=mc` 를 해도 **그 값은 앱에 닿지 않는다.**
`REACHY_LLM_URL` 같은 주소 3종이 처음부터 설정파일 사다리를 타는 것과 같은 이유다
(`apps/voice_chat/voice_chat/config.py` 머리말).

역할이 안 닿으면 로봇은 **조용히 1대 모드로** 뜬다 — 로그는 정상으로 보인다.

### 노트북(무대감독)에서 — 여기는 셸이 맞다

무대감독은 노트북에서 직접 실행하는 프로세스라 export 가 그대로 먹는다.

```bash
export REACHY_MC_UNIT=<사회자 hardware_id>        # §3 에서 채취한 값
export REACHY_DOCENT_UNIT=<도슨트 hardware_id>
export REACHY_DIRECTOR_PORT=8777
```

### 각 로봇에는 — `./reachy.sh robot up` 이 설정파일에 써 넣는다

`./reachy.sh start --robot`(§7)이 두 로봇에 이 일을 **한 번에** 한다 — 역할은 사회자/도슨트로
정해 넣고, 감독 주소는 이 노트북(`ws://<LAN IP>:8777`)으로 넣는다. 아래는 부품별로 띄울 때다.

노트북에서 로봇마다 한 번씩 돌린다. 역할·무대감독 주소·추론 3종 주소가
로봇의 `~/.config/reachy-mini-voice-chat/config.json` 에 들어간다.

```bash
REACHY_ROLE=mc     REACHY_ROBOT_HOST=192.168.0.4 ./reachy.sh robot up
REACHY_ROLE=docent REACHY_ROBOT_HOST=192.168.0.5 ./reachy.sh robot up
```

`REACHY_ROLE` 없이 돌리면 그 로봇의 역할 설정을 **지운다**(1대 모드로 되돌린다).
지웠다는 줄이 화면에 뜬다 — 안 떴으면 안 지워진 것이다.

확인:

```bash
ssh pollen@192.168.0.4 cat .config/reachy-mini-voice-chat/config.json
# {"REACHY_LLM_URL": ..., "REACHY_ROLE": "mc", "REACHY_DIRECTOR_URL": "ws://192.168.0.10:8777"}
```

앱 기동 로그에도 출처가 같이 찍힌다 — `무대감독: ws://… (설정파일)  역할: mc (설정파일)`.
`(기본값)` 이라고 나오면 값이 안 닿은 것이다.

### `scripts/stage-env.sh` 는 언제 쓰나

로봇에서 앱을 **손으로** 띄울 때만 쓴다(`.venv/bin/python main.py`). 데몬이 띄우는
정상 경로에서는 닿지 않는다. 이 스크립트는 `REACHY_MC_UNIT`/`REACHY_DOCENT_UNIT` 을
다루지 않는다 — 그 둘은 위의 **노트북** 쪽 값이다.

```bash
PC_IP=192.168.0.10 source scripts/stage-env.sh mc       # 로봇에서 손으로 띄울 때만
```

음성(사회자 `serena` / 도슨트 `sohee`)은 `main.py` 가 역할에 맞춰 자동으로 넣는다 —
**환경변수든 설정파일이든 `TTS_QWEN_VOICE` 를 직접 적으면 그쪽이 이긴다.**

## 7. 기동 순서

```
① 공유기 켜기
② 로봇 2대 켜고 WiFi 붙는 것 확인 (curl 로 status 200)
③ 한 줄로 전부     ./reachy.sh start --robot
```

`start --robot` 이 **추론 3종(LAN) → 예열 → 사회자·도슨트 각각(도달 확인 → 백엔드 상태/복구 →
config 동기화 → 로봇→맥 도달 → 기상 → 앱) → 무대감독(0.0.0.0, 이 터미널이 콘솔) + 대시보드**
를 순서대로 한다. 로봇 주소 기본값은 §2 의 `192.168.0.4`(사회자) / `192.168.0.5`(도슨트)다 —
§2 에서 다른 주소를 줬을 때만 `REACHY_MC_HOST=… REACHY_DOCENT_HOST=…` 로 덮어쓴다.
먼저 `--dry-run` 으로 계획만 찍어 볼 수 있다.

- **추론 서버가 LAN 에서 안 보이면 멈춘다** — `start --sim`/`demo` 가 loopback 으로 띄워 남긴
  서버를 재사용하면 로봇이 못 붙는다(`loopback 전용 … ./reachy.sh stop 후 다시`).
- **TTS 가 안 떠도 멈춘다** — 로봇 앱은 이 노트북의 TTS 로만 말한다. 시뮬처럼 say 로 물러나는
  길이 로봇에는 없다(`tail -30 .demo-logs/tts.log`).
- 로봇에 앱이 이미 돌고 있으면(지난 시연의 옛 config) 멈추고 새 config 로 다시 띄운다 — 경고가 뜬다.
- 로봇에 앱이 이미 돌고 있어 멈췄으면 **다시 깨운 뒤**(모터 → wake_up) 띄운다 — 멈춘 로봇은 몇 초 뒤
  절전에 들어, 그대로 띄우면 말은 하는데 몸이 안 움직인다.
- 한 대가 안 닿으면 **경고하고 건너뛴다** — 감독은 남은 한 대로 뜬다(1인 모드, 아래 ⚠️). 건너뛸 때마다
  그 로봇의 합류 명령(`REACHY_ROLE=<역할> REACHY_ROBOT_HOST=<주소> ./reachy.sh robot up`)이 찍힌다.
- 무대감독·대시보드 포트(8777·8778)를 누가 쥐고 있으면 그게 무엇인지 보여 주고 멈춘다.
- `REACHY_MC_HOST` 와 `REACHY_DOCENT_HOST` 가 같으면 멈춘다(종료코드 2, `--dry-run` 도) — 도슨트 config 가
  사회자를 덮어쓴다.
- 콘솔 `q`(또는 Ctrl-C)로 끝내면 **두 로봇(사회자·도슨트 주소)의 앱만** 멈춘다 — 건너뛰었다가 위 합류 명령으로
  나중에 붙인 로봇까지. 그때도 꺼져 있는 로봇은 `로봇 앱 정지 실패 … 안 닿는다` 한 줄이 뜬다. 추론 3종은
  남는다 — 전부 내리려면 `./reachy.sh stop`.

**부품별로 띄울 때**(한 대만 다시 올리거나 어느 단계에서 막히는지 좁힐 때) — 위 ③ 한 줄을 셋으로 나눈 것이다:

```
③-1 무대감독 기동                 .venv/bin/python -m stage
③-2 사회자 로봇 기동   REACHY_ROLE=mc     REACHY_ROBOT_HOST=… ./reachy.sh robot up
③-3 도슨트 로봇 기동   REACHY_ROLE=docent REACHY_ROBOT_HOST=… ./reachy.sh robot up
```

`robot up` 하나가 **추론 3종 기동 → 예열 → config 동기화 → 기상 → 앱 기동**을 순서대로
한다(예열은 2026-09-22 에 로봇별 단계 앞으로 옮겼다 — `start --robot` 이 두 대에 한 번만 하려고). 두 번째 호출에서 추론 3종과 예열은 이미 돼 있으므로 금방 지나간다.

> **⚠️ 예열을 건너뛰지 않는다.** Qwen3-TTS 첫 합성은 Metal 커널 JIT 로 **8.5초**가
> 걸린다(`scripts/warmup.py` 실측). 감독의 타임아웃 여유분(`TIMEOUT_MARGIN_S`)을 15초로
> 잡아 **예열을 빠뜨려도 헛타임아웃은 나지 않게** 해 뒀지만, 그건 방어선이지 대체재가
> 아니다 — 예열을 하면 첫 발화가 8.5초 빨라진다. 시연 첫 인상이 걸린 구간이다.
> `robot up` 이 "예열을 건너뛰었다" 고 찍으면 `./reachy.sh warmup` 을 따로 돌린다.
> 근거와 수치는 `docs/real-robot-deployment.md` §15.2-3.
>
> 로봇에서 앱을 손으로 띄우는 경우에도 노트북에서 `./reachy.sh serve` 와
> `./reachy.sh warmup` 을 먼저 돌린다.

무대감독 콘솔에 두 로봇이 붙었다는 로그가 뜨면 `s` 를 눌러 시작한다.

| 키 | |
|---|---|
| `s` | 시작 |
| `n` | 다음 큐 — 발화 중이든 `a` 로 멈춘 뒤든 먹는다 |
| `p` | **이전 큐** — 오인식으로 섹션이 넘어가 버렸을 때 되돌린다 |
| `r` | 현재 큐 다시 |
| `a` | 즉시 중단 |
| `q` | 종료 |

`n`·`p`·`r` 는 먼저 양쪽을 중단시킨 뒤 그 큐를 시작한다 — 대개 잘못 넘어간
대사가 흐르는 중에 누르기 때문이다. `s` 를 두 번 누르면 `거절됨: …` 이 뜨고
콘솔은 계속 돈다(예전에는 여기서 무대감독이 통째로 죽었다).

**콘솔은 비상용이다.** 정상 진행은 관람객이 "다음"·"계속" 이라고 말하면 된다.

### 한 큐가 흐르는 모양 (2026-09-14)

```
사회자(주제 넘김) → 도슨트(해설) → 사회자(받아치기 + "질문 있으면 말씀, 아니면 '다음'") → 듣기
                                                                     └ 질문 → 사회자("좋은 질문이네요, 도슨트?") → 도슨트(답) → 듣기
```

**관람객 창구는 사회자가 말로 연다.** 마이크가 열려도 관람객은 그것을 모르므로, 받아치기 끝에
"다음" 을 안내한다. 질문에는 사회자 확인 멘트가 먼저 나가고 그동안 답을 만든다 — 질문 뒤 정적이
없어야 정상이다. 정적이 있으면 감독 로그에서 `대사 생성이 늦다 — 폴백` 을 찾는다.

로봇 로그에서 볼 것: 사회자가 도슨트 말을 받아적으면 `[마이크 닫힘 — 버림: …]` 이 **아니라**
아무 줄도 없어야 한다(캡처 단에서 막는다). `청취 루프가 죽었다` 가 뜨면 콘솔로 진행한다.

### ⚠️ 사회자가 빠진 1인 모드는 **콘솔로만 진행한다**

관람객 창구는 사회자 하나다(설계 §2). 도슨트 로봇은 STT 청취 루프를 아예 띄우지
않는다 — 두 대가 다 들으면 PC 추론 부하가 두 배가 된다.

그래서 **사회자가 끊겨 도슨트만 남은 1인 모드**에서는 관람객이 "다음"이라고 말해도
아무 일도 일어나지 않는다. 감독은 규약대로 `mic(open=true)` 를 보내지만 받을 루프가
없다. 이때 로봇 로그에 이런 줄이 뜬다:

```
  [경고] 마이크를 열라는 지시를 받았지만 이 로봇에는 청취 루프가 없다 — …
```

이 줄을 보면 **콘솔의 `n`/`p` 로 진행한다.** 도슨트가 끊긴 반대 경우(사회자만 남음)는
사회자가 원래 듣고 있으므로 관람객 발화로 그대로 진행된다.

## 8. 시연 전 마지막 확인

- [ ] 두 로봇 다 `curl .../api/daemon/status` 가 200
- [ ] `hardware_id` 두 개가 설정값과 일치 (무대감독이 기동 시 확인해준다)
- [ ] 두 로봇 startup-app 비어 있음
- [ ] `REACHY_AEC` **꺼짐** — 실기는 XMOS 하드웨어 AEC 가 그 자리를 대신한다
- [ ] 기동 로그에 추론 3종 주소가 노트북을 가리킴 (loopback 이면 경고가 뜬다)
- [ ] 한 큐를 끝까지 돌려본다: 사회자 → 도슨트 → **사회자 받아치기** → "다음"
- [ ] 질문 하나를 던져 본다: 사회자 확인 멘트 → 도슨트 답 → 다시 듣기. 도슨트 답 뒤에
      **도슨트가 자기 말에 또 답하지 않는지** 30초 지켜본다(자기목소리 루프 — 2026-09-14 고침)
- [ ] 콘솔 `r` 을 사회자 발화 중에 눌러 본다 — 두 로봇이 **동시에** 말하면 안 된다
- [ ] 사회자 앱을 껐다 켜 본다(`robot down` → `robot up`) — 다시 붙은 뒤 관람객 "다음" 이 먹는지
- [ ] **로봇 한 대를 일부러 꺼본다** — 남은 한 대가 양쪽 대사를 읽는지(1인 모드),
      경고가 누가 끊겼는지 말하는지
- [ ] **역할을 일부러 바꿔 걸어 본다** — `REACHY_MC_UNIT` 에 도슨트 값을 넣고 기동해
      **정말 실패하는지** 확인한다. 이 분기는 시뮬에서 한 번도 안 돌아 봤다
      (`unit_id` 가 시뮬에서 언제나 `null` 이라 "없으면 통과" 쪽만 실행된다)
- [ ] 콘솔에서 `s` 를 **두 번** 눌러 본다 — `거절됨: …` 이 뜨고 콘솔이 살아 있어야 한다.
      그리고 도슨트 답이 **한 번만** 나온다(예전엔 두 번째 `s` 가 이력을 오염시켰다)
- [ ] 예열이 실제로 됐는지 — 첫 큐의 사회자 발화가 8초 넘게 안 나오면 예열이 빠진 것이다
      (타임아웃은 안 나지만 — 여유분 15초가 덮는다 — 시작이 그만큼 늦다)
