# Director 진입 락에서 블로킹 I/O를 걷어낸다

## 배경

`docs/lessons.md`의 **"락을 쥔 채 네트워크를 기다리지 않는다"**(리뷰 C1/B3, 2026-09-14)는
관람객 질문의 LLM *요청* 쪽에만 적용됐다. 같은 락 아래에 블로킹이 두 군데 남아 있다.

1. **소켓 쓰기** — `Director._emit()` → `self._send` → `StageServer._send` → `ws.send()`.
   모든 공개 진입점이 `self._lock` 을 쥔 채 이 경로를 탄다. 한쪽 로봇의 링크가
   반열림(WiFi 순단 등)이면 송신 버퍼가 차 `ws.send()` 가 막히고, **감독 전체**가
   그동안 멈춘다 — `abort()`·`tick()`·`on_heard()` 전부. websockets keepalive
   (`ping_interval=20`/`ping_timeout=20`)가 끊어줄 때까지 **최대 약 40초**다.

2. **생성 결과 대기** — `on_speaking_ended()` 가 락을 쥔 채
   `_speak_pending()` → `_pending_ready.wait(GENERATE_GRACE_S)` 로 **최대 8초** 기다린다.
   `abort()` 의 docstring 은 "즉시 중단"이라고 적혀 있지만, 사회자 발화가 끝나고
   도슨트 대사를 기다리는 이 구간에서 콘솔 `a` 는 최대 8초 먹지 않는다.

`__init__` 의 `self._lock` 주석은 2번을 "의도한 동작"이라 적어 뒀다. 당시 근거는
"핸드오프 중에는 아무것도 타임아웃돼서는 안 된다" 였는데, 그 보호는 이미
`self._deadline = None` 이 하고 있다. 락이 추가로 하는 일은 **운영자의 비상정지를
막는 것**뿐이다.

목표: 진입 락은 상태 작업만 덮는다. 락의 의미를 바꾸는 것이 아니라, 락 아래에서
블로킹하던 두 가지를 각각 제자리에서 없앤다.

## ~~① 소켓 쓰기 — `stage/server.py` 에 연결별 송신 스레드~~ (이번 범위 밖)

**2026-09-20 판단: 하지 않는다.** 맥의 기본 `SO_SNDBUF` 가 131072 바이트이고
감독이 보내는 `say` 한 통이 328 바이트다 — `ws.send()` 가 실제로 막히려면 약
400통이 밀려야 하는데 19섹션 시연 전체가 80통 남짓이다. 이 workload 에서는
사실상 도달하지 않는 경로에 연결별 큐·스레드·수명관리를 들이는 값이 없다.
구조적 위험 자체는 참이므로 `docs/real-robot-deployment.md` 에 남은 위험으로
적는다(아래 설계는 필요해질 때를 위해 남겨 둔다).

`Director` 는 전송을 모른다(`send(role, cmd)` 콜러블만 받는다). 막히는 것은 전송
계층이므로 거기서 고친다. `_send` 가 즉시 반환하면 감독 락이 I/O를 덮는 일 자체가
없어지고, **감독이 계산한 지시 순서 = 와이어 순서** 보장도 그대로 남는다.

- 연결마다 `queue.Queue(maxsize=64)` + 데몬 송신 스레드 하나(`_Sender`).
- `StageServer._send` 는 "붙지 않았다" 경고(동기, 기존과 같음) 뒤 `put_nowait` 만 한다.
- 큐가 차면 **버리고 시끄럽게 경고한다**(한 턴이 최대 4통이라 64면 링크가 죽은 것).
- `ws.send()` 예외 경고는 송신 스레드에서 남긴다(지금도 경고만 하고 삼킨다).
- `_conns` 가 ws 대신 `_Sender` 를 담는다. 중복 연결 정리(`old.close()`)와
  `finally` 의 `is ws` 동일성 검사는 `_Sender` 기준으로 옮긴다. 종료는 센티넬 +
  짧은 join(막힌 send 에 매달리지 않는다).

**아는 비용**: 두 링크가 모두 건강할 때 로봇 간 지시 순서에 1ms 미만의 엇갈림이
생길 수 있다(로봇별 순서는 FIFO로 엄격히 보존된다). 한쪽이 정체된 경우 그 로봇은
어차피 닿지 않는 상태이고, 재접속 때 `on_connect` → `_resync_mic` 가 마이크 상태를
다시 맞춘다.

## ② 8초 생성 대기 — `Director.on_speaking_ended` 를 락 두 구간으로 나눈다

```
[락] machine.on_speaking_ended → 유령이면 종료 / _deadline=None / 어느 갈래인지 판정
     · 받아치기·평범한 듣기 갈래는 여기서 _emit 하고 끝낸다(지금과 동일)
     · 도슨트 해설·질문 응답 갈래는 기다릴 Event 를 찍어만 두고 락을 놓는다
[락 밖] _await_pending(ready, fallback, label)   ← 최대 GENERATE_GRACE_S
[락] 상태가 아직 LISTENING 인가? 아니면 얹지 않고 경고하고 물러난다
     맞으면 _remember + machine.speak + _emit
```

- **대기 중 mic-open 을 내보내지 않는다.** `machine.on_speaking_ended` 가 돌려준
  mic-open 지시는 2구간까지 들고 갔다가 도슨트의 mic-close 와 **한 번에** `_emit`
  한다 — `coalesce` 가 덮으므로 마이크는 지금처럼 깜빡이지 않는다. 취소되면 통째로
  버린다(끼어든 쪽이 이미 제 지시를 내보냈다).
- **취소 판정은 상태 + 세대 토큰 둘로 한다.** 새 플래그는 만들지 않는다 —
  둘 다 이미 있는 것이다.
  - `abort()` 는 `IDLE` 로 가므로 **상태**가 잡는다.
  - `next()`/`previous()`/`start()` 도 `MC_SPEAKING` 으로 가지만, 상태만 보면
    못 잡는 틈이 있다: 대기 중 `n` → 새 사회자 대사가 짧아 대기가 끝나기 전에
    발화가 끝나면 상태가 **다시 LISTENING** 이 된다. 그대로 두면 2구간이
    깨어나 **이전 섹션의 도슨트 대사**를 읽고, 뒤이어 새 큐의 핸드오프가
    `TurnError` 를 맞는다. `_spawn_generate` 가 큐·질문마다 올리는
    **`_gen_token`** 을 1구간에서 찍어 두고 2구간에서 대조해 이것을 잡는다
    (`_generate_pending` 이 늦은 결과를 버릴 때 쓰는 것과 같은 장치다).
  - `tick()` 은 `_deadline` 이 이미 None 이라 무해하다.
- **`_who()` 는 2구간에서 다시 계산한다 — 1구간 판단을 들고 가지 않는다.**
  대기 중 도슨트가 끊기면 고정된 판단은 끊긴 로봇에게 대사를 보내고, 전송
  계층은 "아직 붙지 않았다" 경고만 남기고 버린다. 상태기계는 도슨트가 말하는
  중이라 믿으므로 `speaking_ended` 가 영영 오지 않고 tick 타임아웃까지 15~20초
  정적이 된다. 재계산하면 남은 한 대가 양쪽을 읽는다(설계 §7 1인 모드).
  사회자 몫/도슨트 몫을 가르는 `cue_id` 체계(맨 `cue.id` / `:docent` / `:ack`
  / `:qa` / `:after`)는 손대지 않으므로 1인 모드 판정도 지금 그대로다.
- **아는 변화**: 대기 동안 상태가 LISTENING 이므로 그 사이 로봇이 끊기거나
  다시 붙으면 `on_disconnect`/`_resync_mic` 가 리스너 마이크를 잠깐 실제로
  연다(지금은 락이 막는다). 그 순간 아무도 말하고 있지 않으므로 불변식 ①
  위반은 아니고 2구간의 `speak()` 가 곧 닫는다. 그 틈에 들린 말은 질문으로
  처리되고, 우리 대사는 토큰/상태 검사에서 경고를 남기고 물러난다.
- `_await_pending` 은 폴백을 **반환만** 한다 — 지금은 유예 초과 시 `_gen_lock` 없이
  `self._pending_text` 에 써서 생성 스레드의 결과를 덮어쓸 수 있었다(경합). 쓰지
  않으면 경합 자체가 없어진다.
- 대기할 `Event` 는 락 안에서 찍어 둔다 — 대기 중 `_spawn_generate` 가 슬롯을 갈면
  우리는 우리 세대의 결과를 기다린 뒤 상태 검사에서 물러난다.
- `_speak_pending`/`_speak_docent` 는 이 구조로 흡수된다.

## 검증

TDD — 아래 넷을 **먼저 써서 실패를 보고** 고친다.

1. `test_도슨트_생성_대기가_abort_를_막지_않는다` — 생성을 막아 둔 채
   `on_speaking_ended("mc","c1")` 를 스레드로 돌리고, `d.abort()` 가 1초 안에
   돌아오는지. (지금은 약 8초. 기존
   `test_질문_응답_생성은_on_heard_를_막지_않는다` 와 같은 모양)
2. `test_대기_중_abort_가_나면_도슨트가_뒤늦게_말하지_않는다` — 대기 중 abort 뒤
   생성을 풀어도 도슨트 `say` 가 나가지 않고 상태가 IDLE 로 남는지. (이번 리팩터링이
   새로 들일 수 있는 경합을 박제한다)
3. `test_대기_중_next_가_끼어들면_옛_도슨트_대사는_버려진다` — `TurnError` 가
   새어 나오지 않고 옛 대사도 나가지 않는지.
3b. `test_대기_중_다음_큐가_돌아_LISTENING_이_돼도_옛_대사는_안_나간다` —
   상태만 보는 판정으로는 못 잡는 틈(위 §② 참고)을 세대 토큰이 잡는지.
   `n` 으로 다음 큐를 시작시키고 그 발화까지 끝내 상태를 LISTENING 으로
   되돌린 뒤 대기를 푼다. 이전 섹션 해설이 나가면 실패다.
3c. `test_대기_중_도슨트가_끊기면_남은_사회자가_그_대사를_읽는다` — 역할
   재계산을 값으로 못박는다. 1구간 판단을 고정하면 대사가 버려지고 정적이
   된다.
4. `test_한쪽_전송이_막혀도_다른_로봇은_계속_받는다`(서버) — 한 연결의 send 를
   막아 두고 다른 로봇이 계속 받는지, `director.abort()` 가 즉시 돌아오는지.

회귀로 반드시 그대로 통과해야 하는 것:
`test_타이머와_발화종료가_겹쳐도_불변식이_깨지지_않는다`,
`test_사회자에서_도슨트로_넘어갈_때_마이크가_열리지_않는다`,
`test_사회자_발화가_끝나면_도슨트가_바로_받는다`, 서버 스위트 전체.
